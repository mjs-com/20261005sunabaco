GitHub ブランチ運用ルール
制定日：2026年11月1日
改定日：2026年11月1日（一人開発向け）

1. 基本方針
・main を開発の基準とし、ビルドと必要なテストが通る状態を保つ。
・機能追加、修正、文書変更は、最新の main から専用ブランチを作る。
・1ブランチは1つの目的とし、小さな単位で早めに取り込む。
・main への変更は必ずプルリクエスト（PR）を経由する。直接 push しない。
・常設の develop ブランチは設けない。

2. ブランチの命名規則
・半角英小文字・数字・ハイフンを使い、「種類/内容」の形式に統一する。
・Issue がある場合は「種類/Issue番号-内容」とする。

  feature/12-add-login       機能追加
  fix/25-login-error         不具合修正
  docs/update-readme        文書変更
  chore/update-dependencies  依存関係・設定・保守作業
  hotfix/fix-startup         緊急修正（通常と同じPR・確認が必要）

3. 標準的な作業手順
(1) 未コミットの変更を確認し、コミットまたは退避してから切り替える。
(2) main を更新し、作業ブランチを作る。

    git switch main
    git pull --ff-only origin main
    git switch -c feature/12-add-login

(3) 変更を実装し、対象に応じたテスト・ビルド・動作確認を行う。
(4) 変更内容を確認し、対象ファイルだけをコミットして push する。

    git add <対象ファイル>
    git commit -m "ログイン機能を追加"
    git push -u origin feature/12-add-login

(5) GitHub で取り込み先を main にした PR を作成する。
(6) 自己レビューと必要な確認を終え、Squash and merge で取り込む。
(7) 取り込み済みの作業ブランチを削除する。次の作業には再利用しない。

4. PR の記載内容とマージ条件
・PR には目的、変更点、関連 Issue、確認手順と結果を記載する。
・画面変更は必要に応じて画像を添え、未確認の事項は明記する。
・作業途中は Draft PR とし、マージしない。
・一人開発では第三者の承認を必須としない。PRは必ず作成する。
・作成者が差分を自己レビューし、要件との一致と確認結果をPRに記録する。
・指摘への対応を終え、未解決のレビュー会話がないことを確認する。
・利用中の CI がある場合は、必須チェックがすべて成功していること。
・CI が未整備の場合も手動の確認結果を残す。未実施を「成功」としない。
・コードを変更した場合は、自己レビューと必要なテスト・動作確認を再実施する。

5. 競合と履歴の扱い
・競合は作業ブランチに最新の origin/main をマージして解消する。
・解消後は関係するテストと動作確認を再実施する。
・共有ブランチへの force push と main の履歴書き換えは禁止する。
・長期化する作業は分割し、必要なら機能フラグで未完成部分を無効にする。

6. リリースブランチ（複数バージョンの保守が必要な場合のみ）
・必要になった時点で main から release/1.0 のようなブランチを作る。
・リリース固有の修正は、その release ブランチから作業ブランチを作り、
  PR で同じ release ブランチに取り込む。確認・承認条件は main と同じ。
・main にも必要な修正は、main から別ブランチを作り、該当コミットを
  cherry-pick して別の PR で取り込む。両方の PR を相互に関連付ける。
・release ブランチ全体を main にマージしない。保守終了後はロックする。

7. GitHub 側で設定する保護ルール
この文書を保存するだけでは GitHub の設定は変更されない。
管理者は main と、利用する場合は release/* に対して、次を設定する。
・PR 経由のマージを必須にし、必要な承認数は0名とする。
・コードオーナーや直近のpushに対する第三者承認も要求しない。
・承認は必須にせず、古い承認を無効にする設定も無効とする。
・レビュー会話の解決は引き続き必須とする。
・CI 導入後は、実際に動作するチェックを必須に指定する。
・force push とブランチ削除を禁止し、管理者を含む迂回を許可しない。
・作業ブランチには Squash and merge を使う運用に統一する。

8. 参考資料と本プロジェクトでの決定
Microsoft Learn「Git ブランチ戦略を採用する」
https://learn.microsoft.com/ja-jp/azure/devops/repos/git/git-branching-guidance?view=azure-devops
参照日：2026年11月1日

資料の基本方針をもとに、命名形式、PR必須、Squash and merge、
develop を常設しないことを本プロジェクトの運用ルールとして定めた。
一人開発に合わせ、第三者の承認は必須とせず、自己レビューと検証結果の記録を行う。


9. 数当てゲームの実行方法
プロジェクト直下で次のコマンドを実行する。

    C:\Python313\python.exe -B number_guessing.py

PythonがPATHに設定されている環境では python -B number_guessing.py でも実行できる。
1〜100の整数を10回以内に当てる。qで終了し、勝敗確定後はyで再プレイ、nで終了する。

テスト実行：

    C:\Python313\python.exe -B -m unittest discover -s tests -v
